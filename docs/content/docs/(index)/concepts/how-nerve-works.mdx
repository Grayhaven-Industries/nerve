---
title: How Nerve works
description: The stages a harness passes through, and what each stage is allowed to know.
---

Nerve is a compiler with a fixed pipeline. Understanding which stage owns
which fact explains most of its behaviour, including why some checks stay
silent until you supply more data.

```text
input            →  HIR             →  rules            →  artifacts
.harness.ts         harness.json       HK-* findings       drawings, tables,
WireViz YAML        versioned,         severities,         test plan, PDF,
CSV / Excel         canonically        margins             packet, records
KiCad / tscircuit   sorted
```

## 1. Input

Several front ends produce the same thing. The TypeScript
[DSL](/docs/reference/dsl) is one of them, not a prerequisite:

- `.harness.ts` files, loaded directly by the CLI. No build step.
- WireViz YAML, including projects that keep reusable anchors in a separate
  prepend file.
- CSV and Excel wire lists, through an explicit column map.
- Connector contracts from KiCad boards, pinout CSV, tscircuit, and Nerve's
  own JSON.

Importers never guess. Every accepted or rejected source row stays visible in
the import report with row and column diagnostics, and anything that cannot be
represented without loss becomes a diagnostic rather than a silent
approximation.

## 2. HIR

`compileDesign` lowers the design graph to the **harness intermediate
representation**. HIR is a versioned schema, canonically sorted, with optional
fields omitted rather than set to null. See the
[HIR reference](/docs/reference/hir).

Two properties matter downstream:

- **Everything else reads HIR only.** Rules and exporters never see your
  TypeScript, your YAML, or your spreadsheet. A WireViz import and a
  hand-authored design that describe the same harness are judged identically.
- **It is content-addressable.** The fingerprint printed by `nerve review` and
  `nerve release` is a hash of the HIR, so a packet can be checked against the
  release it claims to come from.

## 3. Rules

The rule set runs over HIR and reports findings. A finding carries a stable
code, a severity, a target, and a message.

```text
error  connector:J1.pin:1  HK-MFG-004
  Wire W1 uses 10AWG but connector J1 accepts 24AWG to 32AWG.
```

Codes are stable across releases, which is what makes them usable in CI
allowlists, waivers, and process documents. Severity drives the exit code:
errors exit `1`, warnings do not. Severities are tunable per rule without
forking it, and releases fail closed on any error.

Two design decisions are worth knowing:

- **Checks judge against the part, not against the design's own claims.** A
  wire is judged against the contact that crimps it, not against the housing.
  A pin is judged against the pinout its part fixes, not against what the
  design says about itself.
- **A check that lacks facts stays silent rather than guessing.** `nerve parts`
  tells you which checks a given part currently enables and which are inactive
  for want of data. This is why
  [rule coverage](/docs/reference/rule-coverage) matters more than the rule
  count.

## 4. Artifacts

Exporters turn HIR into the things a shop actually uses: drawings, BOM, cut
list, labels, bill of process, continuity tests, assembly instructions, and a
PDF packet. The renderer never owns truth. Every line in every artifact traces
back to a design object in the HIR, and `render-layout.json` records the exact
geometry each renderer consumed so it is diffable outside Nerve.

## 5. Records

After release, the same fingerprint threads through build records, redlines,
and the next revision. See
[the production lifecycle](/docs/concepts/production-lifecycle).
