---
title: Write a custom rule
description: Ship your shop's policy as a package with its own stable codes.
---

A rule is a named function over the HIR with a stable code. Built-in rules and
your rules use the same API, run in the same pass, and produce the same kind of
finding.

## Write it

```ts title="rules/shop-rules.ts"
import { rule } from '@grayhaven/nerve'

export const maxBundleLength = rule(
  'maxBundleLength',
  (ctx) => {
    for (const b of ctx.hir.branches) {
      // A branch carries nominalLength, and routedLength when waypoints let
      // the compiler measure it. There is no plain `length` on a branch.
      const length = b.routedLength ?? b.nominalLength
      if (length !== undefined && length > 2000) {
        ctx.report({
          severity: 'error',
          target: `branch:${b.id}`,
          message: `Branch ${b.id} is ${length}mm; shop limit is 2000mm.`,
        })
      }
    }
  },
  { code: 'SHOP-001' }
)
```

Three things make a rule usable a year later:

- **A stable code.** `HK-*` is reserved for built-ins. Use your own prefix, and
  never reuse a retired code for a different check.
- **A target.** Point at the design object (`branch:SPINE`, `wire:W1`,
`connector:J1.pin:3`). The finding then lands somewhere in a drawing and in a
diff.
- **A message that names the limit.** `is 2400mm; shop limit is 2000mm` tells
  a reader what to change. `exceeds shop limit` does not.

## Register it

`plugins` takes module paths, not rule objects, so export a plugin from the
same file:

```ts title="rules/shop-rules.ts"
import { definePlugin, HIR_SCHEMA_VERSION, rule } from '@grayhaven/nerve'

export const maxBundleLength = rule(/* as above */)

export default definePlugin({
  name: 'acme-shop-rules',
  hirSchemaVersions: [HIR_SCHEMA_VERSION],
  rules: [maxBundleLength],
})
```

```ts title="nerve.config.ts"
import { defineConfig } from '@grayhaven/nerve'

export default defineConfig({
  entry: './src/main.harness.ts',
  plugins: ['./rules/shop-rules.js'],
  rules: { missingWireColor: 'error' },
})
```

Paths are resolved relative to the harness file. The CLI loads each module and
rejects anything that is not a `definePlugin` default export, so a plain object
of rules fails to load. Severities for built-in and custom rules live in the
same `rules` map, keyed by rule name.

## Run rules without the CLI

`runRules` is the same call the CLI makes, so a custom tool gates identically:

```ts
import { compileDesign, hasErrors, runRules } from '@grayhaven/nerve'
import { builtinRules } from '@grayhaven/nerve-rules'
import { maxBundleLength } from './rules/shop-rules.js'
import design from './src/main.harness.js'

const { hir } = compileDesign(design)
const diagnostics = runRules(hir, [...builtinRules, maxBundleLength])

if (hasErrors(diagnostics)) {
  for (const d of diagnostics) {
    console.error(`${d.code} ${d.severity}: ${d.message}`)
  }
  process.exit(1)
}
```

## Where a rule belongs

Validation ownership follows the earliest layer that can know the truth. Before
writing a rule, check which layer owns the fact:

- The **compiler** owns unconditional structural invariants: reference
  integrity, unique identities, valid quantities, coherent cable-conductor
  assignments.
- **Generic rules** own conclusions that follow from declared facts.
- **Shop profiles** own capability limits: approved tooling, sleeve capacity,
  tolerances, local process requirements. Most custom rules belong here.
- **Standards profiles** own versioned policy: identification schemes, derating
  tables, environmental rules, acceptance-test programs.

A generic rule must not claim standards compliance, and a policy rule must not
guess facts the HIR cannot represent. See
[harness modeling](/docs/concepts/harness-modeling).
